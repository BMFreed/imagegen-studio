# PP-001: Понятный интерфейс вместо собираемого workbench — Supporting Contract

Нормативные правила для [PP-001: Понятный интерфейс вместо собираемого workbench](../product-promises.md#pp-001-понятный-интерфейс-вместо-собираемого-workbench).
Краткое обещание и его публичный статус находятся в реестре; этот документ
сохраняет UX-решения, границы, исключения и проверяемые инварианты.

**Область:** application shell, navigation, document tabs, Project screens и
основная композиция рабочих поверхностей.

## Пользовательская выгода

Пользователю не нужно:

- изучать систему docking и layout presets до начала творческой работы;
- решать, в какой части окна должны находиться Prompt, Canvas, Layers, History
  или Project settings;
- поддерживать несколько почти одинаковых раскладок для разных задач;
- запоминать, была ли изменённая композиция сохранена отдельно от проекта;
- восстанавливать рабочий экран после случайной замены или дублирования
  основных инструментов.

Продукт берёт на себя ответственность за информационную архитектуру,
визуальную иерархию и осмысленные сочетания инструментов.

## Явное не-обещание

ImageGen Studio — не IDE, не универсальный workbench и не система dockable
панелей. Продукт не обещает:

- произвольное добавление, удаление и перемещение основных панелей;
- замену одной основной рабочей поверхности любой другой;
- возможность превратить один семантический режим в другой через layout;
- дублирование одного primary tool в нескольких слотах;
- пользовательскую сборку собственных экранов из внутреннего widget registry;
- совместимость с layout-парадигмой VS Code, Visual Studio или сложных DCC/IDE.

Отсутствие docking само по себе не является ценностью. Ценность состоит в том,
что пользователю не требуется проектировать интерфейс перед работой, а каждый
экран остаётся понятным, устойчивым и пригодным для своей задачи.

## Product-owned composition

Основная композиция принадлежит продукту:

- `Home` остаётся экраном организации и открытия `.igs` документов;
- `Project` tab всегда представляет конкретный открытый `.igs` document;
- `Canvas` остаётся рабочей поверхностью внутри Project, а не взаимозаменяемым
  top-level widget;
- Project modes имеют стабильное доменное назначение и не являются именами для
  произвольных layout presets;
- Model Manager, Preset Manager, Queue Manager и другие app-level surfaces не
  превращаются в заменяемые Project panels;
- preset хранит настройки домена, а не композицию интерфейса, если отдельная
  feature specification явно не вводит другой специализированный тип preset.

Названия экранов и режимов являются контрактом. Если пользователь открывает
`Create`, он получает интерфейс создания, а не произвольный набор панелей,
которому когда-то дали это имя.

## Допустимая ограниченная настройка

Opinionated-интерфейс не означает запрет на любую персонализацию. Допустимы
локальные и обратимые настройки, которые не меняют информационную архитектуру:

- изменение размеров заранее определённых split panels;
- collapse и повторное открытие второстепенной панели;
- выбор плотности представления;
- раскрытие и сворачивание секций;
- настройка видимости вспомогательной информации;
- keyboard shortcuts и другие способы ускорить уже определённые действия;
- сохранение domain presets для параметров генерации.

Такие настройки должны сохраняться автоматически либо редактироваться в явном
режиме с понятными `Save` / `Discard`. Переключение экрана, режима или проекта не
может молча уничтожить несохранённую конфигурацию.

Настройка недопустима, если она:

- меняет назначение экрана;
- создаёт бессмысленное или неподдерживаемое сочетание primary tools;
- скрывает обязательное состояние или единственный путь к ключевому действию;
- требует отдельной дисциплины сохранения layout без явного dirty state;
- заставляет пользователя понимать внутреннюю компонентную архитектуру.

## Следствия для UX и архитектуры

1. Document tabs, domain modes и presets являются разными сущностями и не
   подменяют друг друга.
2. Новая рабочая поверхность проектируется вокруг конкретной пользовательской
   задачи, а не как пустой контейнер для зарегистрированных widgets.
3. Общие компоненты можно переиспользовать внутри кода, но их взаимозаменяемость
   не обязана становиться пользовательской функцией.
4. Power-user workflows развиваются через shortcuts, bulk actions, search,
   presets и progressive disclosure, а не через обязательную настройку layout.
5. Навигация сначала сохраняет, flush'ит или явно разрешает dirty state и только
   потом меняет контекст.
6. Любая будущая идея docking/workbench требует пересмотра этого обещания как
   продуктового решения, а не только добавления UI-библиотеки.

## Проверяемые инварианты

Обещание считается соблюдённым, если:

- вкладка проекта однозначно соответствует одному `.igs` document;
- основные экраны и режимы имеют стабильный состав и назначение;
- пользователь не может случайно заменить Canvas на Project settings или
  собрать несколько копий одного primary tool;
- переход между tabs и modes не теряет изменения без предупреждения;
- локальные resize/collapse preferences восстанавливаются предсказуемо;
- для работы в основном flow не требуется создавать или сохранять layout
  preset;
- основные Playwright-сценарии проверяют пользовательскую задачу на штатной
  product-owned композиции, а не только способность widget'ов отрендериться в
  произвольных слотах.

## Допустимые исключения

Специализированная временная композиция допустима для конкретного bounded flow:
например, сравнения вариантов, focus mode или modal manager. Она должна иметь
ясное назначение, безопасный lifecycle и определённый продуктом состав.

Такое исключение не превращает application shell в workbench и не даёт
пользователю обязанность самостоятельно собирать рабочую среду.
