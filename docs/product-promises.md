# Product Promises

Этот документ фиксирует продуктовые обещания ImageGen Studio и явные
не-обещания рядом с ними. Это нормативные ограничения для product scope, UX,
прототипов и production-реализации, а не набор маркетинговых слоганов.

Публично использовать обещание можно только тогда, когда его подтверждают
реальный пользовательский flow, UI и тесты. До этого оно остаётся принятым
направлением продукта и ограничивает новые решения, но не выдаётся за уже
готовую возможность.

Каждое обещание в этом реестре должно отвечать на четыре вопроса:

1. Что именно получает пользователь?
2. Какую понятную выгоду это даёт?
3. Чего продукт сознательно не обещает?
4. Подтверждено ли обещание реальным пользовательским flow?

Точные domain contracts, UX-решения, data boundaries, prototype gaps и
проверяемые инварианты живут в linked supporting contracts. Они доказывают и
ограничивают обещание, но не должны превращать его формулировку в feature spec.

## PP-001: Понятный интерфейс вместо собираемого workbench

**Статус:** принято как продуктовое направление.

**Область:** application shell, navigation, document tabs, Project screens и
основная композиция рабочих поверхностей.

### Обещание

ImageGen Studio предоставляет продуманный и предсказуемый интерфейс для каждого
этапа работы. Проект открывается уже готовым к использованию: экраны сохраняют
своё назначение, инструменты находятся на ожидаемых местах, а переключение между
проектами и режимами не уничтожает работу.

Короткая внутренняя формулировка:

> Opinionated by design: пользователь работает над изображением, а не над
> раскладкой приложения.

Ещё короче границу ответственности можно выразить так:

> Пользователь настраивает свою работу, но не собирает само приложение.

### Пользовательская выгода

Пользователю не нужно:

- изучать систему docking и layout presets до начала творческой работы;
- решать, в какой части окна должны находиться Prompt, Canvas, Layers, History
  или Project settings;
- поддерживать несколько почти одинаковых раскладок для разных задач;
- запоминать, была ли изменённая композиция сохранена отдельно от проекта;
- восстанавливать рабочий экран после случайной замены или дублирования
  основных инструментов.

Продукт берёт на себя ответственность за информационную архитектуру,
визуальную иерархию и осмысленные сочетания инструментов.

### Явное не-обещание

ImageGen Studio — не IDE, не универсальный workbench и не система dockable
панелей. Продукт не обещает:

- произвольное добавление, удаление и перемещение основных панелей;
- замену одной основной рабочей поверхности любой другой;
- возможность превратить один семантический режим в другой через layout;
- дублирование одного primary tool в нескольких слотах;
- пользовательскую сборку собственных экранов из внутреннего widget registry;
- совместимость с layout-парадигмой VS Code, Visual Studio или сложных DCC/IDE.

Отсутствие docking само по себе не является ценностью. Ценность состоит в том,
что пользователю не требуется проектировать интерфейс перед работой, а каждый
экран остаётся понятным, устойчивым и пригодным для своей задачи.

### Product-owned composition

Основная композиция принадлежит продукту:

- `Home` остаётся экраном организации и открытия `.igs` документов;
- `Project` tab всегда представляет конкретный открытый `.igs` document;
- `Canvas` остаётся рабочей поверхностью внутри Project, а не взаимозаменяемым
  top-level widget;
- Project modes имеют стабильное доменное назначение и не являются именами для
  произвольных layout presets;
- Model Manager, Preset Manager, Queue Manager и другие app-level surfaces не
  превращаются в заменяемые Project panels;
- preset хранит настройки домена, а не композицию интерфейса, если отдельная
  feature specification явно не вводит другой специализированный тип preset.

Названия экранов и режимов являются контрактом. Если пользователь открывает
`Create`, он получает интерфейс создания, а не произвольный набор панелей,
которому когда-то дали это имя.

### Допустимая ограниченная настройка

Opinionated-интерфейс не означает запрет на любую персонализацию. Допустимы
локальные и обратимые настройки, которые не меняют информационную архитектуру:

- изменение размеров заранее определённых split panels;
- collapse и повторное открытие второстепенной панели;
- выбор плотности представления;
- раскрытие и сворачивание секций;
- настройка видимости вспомогательной информации;
- keyboard shortcuts и другие способы ускорить уже определённые действия;
- сохранение domain presets для параметров генерации.

Такие настройки должны сохраняться автоматически либо редактироваться в явном
режиме с понятными `Save` / `Discard`. Переключение экрана, режима или проекта не
может молча уничтожить несохранённую конфигурацию.

Настройка недопустима, если она:

- меняет назначение экрана;
- создаёт бессмысленное или неподдерживаемое сочетание primary tools;
- скрывает обязательное состояние или единственный путь к ключевому действию;
- требует отдельной дисциплины сохранения layout без явного dirty state;
- заставляет пользователя понимать внутреннюю компонентную архитектуру.

### Следствия для UX и архитектуры

1. Document tabs, domain modes и presets являются разными сущностями и не
   подменяют друг друга.
2. Новая рабочая поверхность проектируется вокруг конкретной пользовательской
   задачи, а не как пустой контейнер для зарегистрированных widgets.
3. Общие компоненты можно переиспользовать внутри кода, но их взаимозаменяемость
   не обязана становиться пользовательской функцией.
4. Power-user workflows развиваются через shortcuts, bulk actions, search,
   presets и progressive disclosure, а не через обязательную настройку layout.
5. Навигация сначала сохраняет, flush'ит или явно разрешает dirty state и только
   потом меняет контекст.
6. Любая будущая идея docking/workbench требует пересмотра этого обещания как
   продуктового решения, а не только добавления UI-библиотеки.

### Проверяемые инварианты

Обещание считается соблюдённым, если:

- вкладка проекта однозначно соответствует одному `.igs` document;
- основные экраны и режимы имеют стабильный состав и назначение;
- пользователь не может случайно заменить Canvas на Project settings или
  собрать несколько копий одного primary tool;
- переход между tabs и modes не теряет изменения без предупреждения;
- локальные resize/collapse preferences восстанавливаются предсказуемо;
- для работы в основном flow не требуется создавать или сохранять layout
  preset;
- основные Playwright-сценарии проверяют пользовательскую задачу на штатной
  product-owned композиции, а не только способность widget'ов отрендериться в
  произвольных слотах.

### Допустимые исключения

Специализированная временная композиция допустима для конкретного bounded flow:
например, сравнения вариантов, focus mode или modal manager. Она должна иметь
ясное назначение, безопасный lifecycle и определённый продуктом состав.

Такое исключение не превращает application shell в workbench и не даёт
пользователю обязанность самостоятельно собирать рабочую среду.

## PP-002: Явное намерение вместо магического control

**Статус:** принято как продуктовое направление.

**Область:** inputs, search, creation/import/install flows, selectors, dialogs и
другие интерактивные controls.

### Обещание

Каждый интерактивный элемент ImageGen Studio имеет одну понятную основную роль.
Пользователь до взаимодействия понимает, что произойдёт после ввода, нажатия
или подтверждения.

Продукт не угадывает принципиально разные пользовательские намерения по форме
введённой строки.

Короткая внутренняя формулировка:

> Один control — один явный intent.

### Пользовательская выгода

Пользователю не нужно:

- выяснять опытным путём, ищет поле или создаёт новую сущность;
- помнить, какие URL, paths, identifiers и search queries принимает один input;
- гадать, изменится ли смысл `Enter` при отсутствии результатов;
- разбираться, почему один и тот же control выполняет разные операции на разных
  экранах;
- бояться случайной mutation во время поиска или навигации.

Label, placeholder, surrounding context и доступное primary action заранее
объясняют результат взаимодействия.

### Явное не-обещание

ImageGen Studio не предоставляет магические polymorphic inputs, которые в
зависимости от содержимого могут:

- искать существующие сущности;
- создавать новые сущности;
- импортировать локальный файл;
- сканировать папку;
- устанавливать ресурс по URL;
- искать ресурс во внешнем каталоге.

Read-only narrowing и domain mutation не объединяются в неявный flow. Search
input не становится `Create`, `Import`, `Install` или `Scan` только потому, что
точного результата не найдено или введённая строка похожа на другой source type.

### Один primary intent

Один control может выполнять несколько технических действий, если они
обслуживают одно пользовательское намерение и не меняют ожидаемый результат:

- prompt editor редактирует текст и показывает autocomplete;
- search сопоставляет query с именем, tags и metadata;
- file import определяет формат уже выбранного файла;
- folder picker выбирает folder, а отдельное `Scan` явно запускает сканирование;
- `Install` загружает и проверяет зависимости выбранной модели;
- selector фильтрует варианты и применяет явно выбранный вариант.

Разница является продуктовой, а не технической:

> Допустима техническая сложность внутри одного намерения. Недопустима скрытая
> смена самого намерения.

Если несколько source types приводят к существенно разным validation,
permissions, progress, error или recovery flows, пользователь сначала явно
выбирает flow. Общий backend parser не является основанием объединять их в один
visible input.

### Обязательные глаголы

Mutation должна называться самостоятельным глаголом:

- `Create`;
- `Import`;
- `Install`;
- `Scan`;
- `Apply`;
- `Remove`;
- `Delete`.

Search, filter и select остаются операциями поиска или выбора. Они не получают
скрытый destructive или creative side effect.

Например, Model Manager использует отдельные flows:

- `Search models` фильтрует установленный catalog;
- `Add from CivitAI URL` открывает import flow по URL;
- будущий `Import local file` выбирает конкретный file;
- будущий `Scan folder` выбирает folder и явно запускает scan;
- будущий marketplace search, если будет принят, является отдельным catalog
  surface.

### Проверяемые инварианты

Обещание считается соблюдённым, если:

- placeholder называет один пользовательский intent;
- search input не создаёт, не импортирует и не устанавливает сущность;
- mutation имеет отдельный видимый verb и accessible name;
- пользователь до submit знает тип операции и её основные последствия;
- `Enter` в search не превращается в creation при пустой выдаче;
- control не меняет назначение из-за соседней panel или случайного текущего
  selection;
- разные source types с разными lifecycle получают отдельный явный выбор;
- Playwright tests отдельно проверяют search и каждую mutation, а не один
  universal happy path.

### Допустимые исключения

Creatable selector допустим только для узкой доменной сущности, где создание
является ожидаемой частью самого выбора, создаваемый объект безопасен, а UI явно
показывает отдельный вариант `Create ...`. Само наличие такого паттерна в UI
library не является причиной использовать его.

Command palette также может находить и запускать разные команды, потому что его
явный intent — выбрать command. Он не заменяет domain-specific create/import
flows и не скрывает последствия выбранной команды.

## PP-003: Одна сущность, один владелец и одно каноническое место

**Статус:** принято как продуктовое направление.

**Область:** domain vocabulary, information architecture, ownership, navigation,
resource managers, Project state и placement настроек.

### Обещание

ImageGen Studio использует небольшой и стабильный словарь сущностей. У каждой
сущности есть понятное назначение, владелец, lifecycle и одно каноническое место
управления.

Пользователь может ответить:

- что это такое;
- где это искать;
- откуда оно появляется;
- что с ним можно сделать;
- что произойдёт при удалении;
- чем оно отличается от соседних сущностей.

Короткая внутренняя формулировка:

> Одна сущность — один owner, один lifecycle и один canonical home.

### Пользовательская выгода

Пользователю не нужно выбирать между несколькими похожими containers, чтобы
найти результат, проект или ресурс. Понятия приложения образуют устойчивую
ментальную модель, а повторное использование сущности не создаёт нового места её
владения.

Если две top-level сущности отвечают на один и тот же вопрос — например, «где
моя картинка?» или «где состояние моей работы?» — их граница недостаточно
определена. Их нужно объединить либо дать им разные, явно наблюдаемые lifecycle
и пользовательские роли.

### Явное не-обещание

ImageGen Studio не создаёт несколько равноправных и частично пересекающихся
способов организации одной и той же работы.

Продукт не обещает Invoke-like параллельную иерархию из `Projects`, `Boards`,
`Gallery`, `Media`, `Assets` и `Canvas states`, если новый пользователь не может
однозначно объяснить различие между ними.

Также не допускаются:

- несколько independently stateful manager surfaces для одной сущности;
- полный CRUD одной сущности в нескольких несогласованных местах;
- разные visible names для одного artifact без ясного преобразования;
- placement настройки по близости реализации вместо domain ownership;
- top-level пользовательская сущность только потому, что такой type существует
  в storage или API;
- contextual копия surface, которая незаметно становится вторым владельцем.

### Канонический словарь

Базовые сущности ImageGen Studio имеют следующие роли:

- **Project** — переносимый `.igs` document с Canvas, Layers, editable state и
  историей принятой работы;
- **Workspace** — файловое место хранения Projects;
- **Projects** — cross-workspace view, а не отдельный container или Workspace;
- **Trash** — lifecycle view для удалённых Projects, а не отдельное место их
  обычного хранения;
- **Canvas** — Project-owned рабочая поверхность и текущая композиция, а не
  библиотека результатов;
- **Model** — установленный reusable inference resource, которым владеет Model
  Manager;
- **Preset** — reusable набор generation settings, которым владеет Preset
  Manager;
- **Generation candidate** — временный результат текущего запуска, ещё не
  являющийся частью Project;
- **Raster Layer / raster variant** — результат, который пользователь явно
  принял в состояние Project;
- **Accepted-result history** — derived Project-owned index принятых
  Layers/variants и их provenance, а не второй container для изображений;
- **Provenance** — immutable объяснение того, как конкретный принятый результат
  был получен;
- **Queue item** — frozen выполняемая, ожидающая или завершённая generation job.

`Asset` может существовать как internal storage term, ID или implementation
entity. Это не делает его автоматически полезной top-level пользовательской
категорией. То же правило применяется к `media`, `blob`, `record`, `node` и
другим backend nouns.

### Настройки имеют владельцев

Canonical ownership относится не только к сущностям, но и к параметрам.
Настройка располагается рядом с тем, на что она влияет, а не рядом с компонентом,
через который реализации удобно получить к ней доступ.

Примеры:

- Denoising Strength принадлежит generation/img2img settings, а не Layers;
- layer opacity принадлежит конкретному Raster Layer;
- mask blur принадлежит Mask;
- Bounding Box принадлежит Smart Patch Layer;
- model defaults принадлежат Model Manager;
- текущие generation overrides принадлежат Project generation draft.

Context может временно показать shortcut или summary настройки, но не меняет её
owner и canonical edit surface.

### Много entry points, один owner

Одно каноническое место не означает единственный entry point.

Model Manager можно открыть из Home, app menu, Model selector или
missing-resource diagnostic. Все пути фокусируют одну manager surface и одну
модель состояния; они не создают несколько независимых Model Managers.

Contextual image picker может выбирать изображение для конкретной операции, но
не становится ещё одной полноценной Gallery со своими независимыми selection,
filters и lifecycle.

Короткое правило:

> Много shortcuts к одному владельцу — нормально. Много конкурирующих
> владельцев одной сущности — нет.

Read-only projection также допустима: например, Home `Projects` объединяет
projects из разных Workspaces, но явно остаётся view и не становится новым
местом хранения.

### Проверка новой сущности

Перед добавлением нового visible noun нужно ответить:

1. Какую единственную пользовательскую проблему решает сущность?
2. Кто её владелец и где её canonical management surface?
3. Как она создаётся, сохраняется, перемещается и удаляется?
4. Чем её lifecycle отличается от уже существующей сущности?
5. Может ли пользователь найти тот же artifact под другим top-level noun?
6. Является ли новая сущность продуктовой необходимостью или отражением
   backend/storage architecture?

Если отличие нельзя объяснить одним предложением без `или`, новая сущность не
готова к включению в пользовательскую модель.

### Проверяемые инварианты

Обещание считается соблюдённым, если:

- каждая top-level сущность имеет документированные owner и lifecycle;
- у сущности есть одна canonical management surface;
- альтернативные entry points открывают или фокусируют владельца, а не создают
  independently stateful копию;
- один artifact не получает несколько равноправных пользовательских названий;
- полный CRUD не дублируется в несогласованных местах;
- setting находится в domain section своего владельца;
- deletion semantics однозначны и документированы;
- internal storage nouns не становятся visible navigation без product review;
- тесты entry points проверяют переход к одному canonical state;
- новая сущность проходит ownership/lifecycle questions до реализации UI.

### Допустимые исключения

Contextual picker, read-only projection, summary или deep link допустимы, если
они явно ограничены текущей задачей, не создают отдельный lifecycle и ведут к
каноническому владельцу для полного управления.

Если future global media library действительно получит отдельную
пользовательскую ценность, ownership и отношение к Project/Layers должны быть
сначала зафиксированы пересмотром этого promise. Нельзя ввести её постепенно как
безымянную вторую Gallery.

## PP-004: Управляемая библиотека моделей вместо ручной работы с файлами

**Статус:** принято как продуктовое направление и обязательный MVP scope.

**Область:** Model Manager, установка моделей, source metadata, версии,
обновления, repair и использование reusable generation resources в Projects,
Presets и accepted-result provenance.

### Обещание

ImageGen Studio обращается с моделями как с управляемыми ресурсами, а не как с
набором файлов, которые пользователь должен самостоятельно скачивать,
идентифицировать, именовать и раскладывать по папкам.

Пользователь выбирает конкретную модель и версию, а приложение берёт на себя
получение файла из поддерживаемого источника, загрузку source metadata и preview,
проверку целостности, размещение в managed library, регистрацию версии,
обнаружение дубликатов, проверку обновлений и восстановление известного
отсутствующего или повреждённого файла.

Короткая внутренняя формулировка:

> Пользователь управляет моделями и версиями. Приложение управляет файлами,
> metadata и целостностью библиотеки.

### Пользовательская выгода

Для обычной установки модели пользователю не нужно:

- отдельно скачивать файл в браузере;
- определять, какой файл соответствует нужной CivitAI-версии;
- вручную копировать файл в правильную папку;
- придумывать локальную структуру каталогов и имена файлов;
- отдельно искать preview, trigger words и compatibility metadata;
- запоминать, какая точная версия использовалась в Project или Preset;
- вручную искать замену отсутствующему или повреждённому файлу;
- опасаться, что обновление незаметно изменит существующий Project.

Model Manager показывает библиотеку в пользовательских понятиях: название,
автор, тип ресурса, версия, совместимость, trigger words или activation tokens,
состояние локального файла, использование и доступность обновления.

### Managed lifecycle

MVP использует CivitAI URL как первый поддерживаемый installation source:

1. Пользователь открывает отдельный `Add from CivitAI URL` flow.
2. Приложение получает metadata и показывает import preview до скачивания.
3. Пользователь явно подтверждает установку конкретной версии и файла.
4. Download становится наблюдаемым Model Manager job с progress и error state.
5. Файл скачивается во временный path, проверяется и только затем перемещается в
   managed models directory и регистрируется в SQLite.
6. Установленный ресурс становится доступен во всех selectors через единую
   библиотеку Model Manager.

Установка не начинается скрытно после вставки URL. Search установленной
библиотеки также не превращается в install flow.

### Source metadata и пользовательские настройки

Source metadata загружается из CivitAI и остаётся source-owned информацией. В неё
входят доступные источнику имя, автор, resource type, версия, base model family,
prediction type, описание, preview, trigger words или activation tokens, file
identity, размер, hash и source link.

Пользователь может управлять эксплуатационным поведением ресурса:

- выбирать установленную версию для Project;
- задавать default version для новых selections;
- задавать поддерживаемые generation defaults;
- устанавливать, восстанавливать и удалять версии.

Эти действия не редактируют source metadata. Metadata, скопированная в immutable
accepted-result provenance, не изменяется при refresh, rename, update или remove
ресурса в текущей библиотеке.

### Версионирование и обновления

Версионирование моделей входит в MVP.

- одна CivitAI model identity объединяет доступные и установленные версии;
- каждая точная версия и file hash остаются отдельной resource identity;
- Model Manager обнаруживает доступную более новую версию и показывает update
  state без автоматической установки;
- `Install Version` сначала показывает version/file preview и затем устанавливает
  новую версию рядом со старой;
- несколько версий одной модели могут быть установлены одновременно;
- пользователь явно выбирает `Default` для новых model selections;
- Generate позволяет явно выбрать любую установленную версию;
- изменение default version не переписывает существующие Projects, Presets или
  provenance;
- старую установленную версию можно снова выбрать без восстановления backup;
- удаление версии является отдельным подтверждаемым действием.

Способ и расписание проверки CivitAI на новые версии могут меняться, но
применение обновления всегда требует явного пользовательского действия.

### Целостность и repair

Продукт отвечает не только за успешный download, но и за состояние managed
resource:

- exact duplicate определяется по CivitAI version identity и/или file hash и не
  скачивается повторно по умолчанию;
- файл считается установленным только после доступных size/hash checks;
- missing или corrupted resource получает явный diagnostic;
- известную CivitAI-версию можно восстановить повторной загрузкой именно этого
  файла;
- presets и provenance остаются читаемыми после удаления локального файла;
- наличие другой версии той же модели не маскирует exact-version mismatch.

### Явное не-обещание

ImageGen Studio — не файловый менеджер моделей, не редактор каталожных карточек и
не универсальный model marketplace. Продукт не обещает:

- основной workflow из ручного скачивания и копирования файлов;
- установку произвольного файла только по расширению `.safetensors`;
- один polymorphic input для CivitAI URL, local path, Hugging Face repo и search;
- сохранение пользовательской структуры папок как организации библиотеки;
- полноценный встроенный CivitAI browser, feed или recommendation system;
- поддержку любого файла или любой модели, опубликованной на CivitAI;
- обход авторизации, лицензии или ограничений доступа источника;
- silent auto-update или автоматическую установку всех новых версий;
- перезапись установленной версии новой и автоматическое удаление старых версий;
- ручное редактирование source metadata;
- смену source avatar/preview, автора, описания, compatibility metadata или
  trigger words;
- превращение model card в настраиваемый профиль;
- скрытую destructive conversion исходного `.safetensors`;
- хранение reusable model weights внутри каждого `.igs`;
- model training как часть Model Manager.

Local file import и folder scan могут появиться как отдельные явные flows, но не
превращают Model Manager в browser произвольной файловой системы.

### Проверяемые инварианты

Обещание считается соблюдённым, если:

- CivitAI URL обрабатывается отдельным preview-first install flow;
- пользователь видит модель, точную версию, файл и размер до download;
- install job имеет наблюдаемые progress, status, cancel/retry и error;
- модель регистрируется только после проверки файла;
- exact duplicate не скачивается повторно без явного действия;
- несколько версий одной модели могут существовать одновременно;
- доступная новая версия видима, но не устанавливается автоматически;
- установка обновления не удаляет и не перезаписывает старую версию;
- default version влияет только на новые selections;
- существующие Projects, Presets и provenance сохраняют exact version identity;
- missing или corrupted version можно диагностировать и восстановить;
- model selectors получают ресурсы из одной библиотеки Model Manager;
- model card показывает source metadata, но не редактирует её.

### Текущий статус прототипа

Vue-прототип уже показывает `Installed Versions`, `Install Version`, `Default`,
`Set Default`, import preview и компактный install progress. Эти элементы пока
presentation-only: прототип не обнаруживает обновления, не устанавливает новую
версию, не меняет default version и не моделирует сохранение exact references.

Интерактивный version/update lifecycle является первым приоритетом при следующем
расширении Model Manager prototype. До появления реализованного flow и тестов
PP-004 ограничивает product decisions, но не выдаётся за уже готовую возможность.

## PP-005: Каждый принятый результат помнит, как он был создан

**Продуктовый статус:** принято как обязательный MVP scope.

**Публичный статус:** пока не обещать как готовую возможность — полный flow ещё
не подтверждён прототипом и тестами.

### Обещание

Каждый принятый результат помнит, как он был создан. Пользователь может
посмотреть использованные настройки, сравнить их с текущими и использовать как
основу для нового пресета.

> Принятый результат хранит своё происхождение; текущая работа не переписывает
> прошлое.

### Пользовательская выгода

Пользователь может изучать связь между результатом и настройками генерации, не
восстанавливать их по памяти и не создавать заранее отдельный preset для каждого
удачного изображения.

### Явное не-обещание

ImageGen Studio не обещает:

- автоматически откатывать или изменять текущую работу при просмотре прошлого
  результата;
- превращать сведения о генерации в полную историю всех состояний проекта;
- побитово идентичный output на другом hardware/backend/runtime только на
  основании одинаковых настроек.

### Supporting contract

Точные правила acceptance, immutable provenance, сравнения, preset mapping,
Smart Patch boundaries, storage и проверяемые инварианты определены в
[PP-005 Supporting Contract: Generation Provenance](./features/project/generate-mode/generation-provenance.md).

Связанные domain contracts:

- [Presets](./features/presets.md) — создание редактируемого preset из
  переносимых настроек результата;
- [Smart Patch Layer](./features/project/generate-mode/smart-patch-layer.md) —
  ownership mask, bbox, internal resolution и compositing state;
- [Data Storage](./specs/03-data-storage.md#generation-provenance) — хранение
  provenance внутри `.igs` и границы derived indexes.

Публичный статус меняется с `пока не обещать` только после того, как supporting
contract подтверждён реализованным пользовательским flow, UI и regression
tests.

## Как добавлять следующие обещания

Новые и постепенно обновляемые записи используют ту же структуру:

- `Обещание` — простое описание пользовательского результата;
- `Пользовательская выгода` — зачем это важно в реальной работе;
- `Явное не-обещание` — broad negative scope и граница ожиданий;
- `Supporting contract` — отдельный документ с product, UX, data и architecture
  decisions, prototype gaps и проверяемыми инвариантами;
- `Публичный статус` — `можно обещать`, `обещать аккуратно` или `пока не
  обещать`, подтверждённый фактическим состоянием продукта.
- `Допустимые исключения` — узкие случаи, не размывающие обещание.

Если новое решение конфликтует с принятым обещанием, конфликт должен быть
назван явно. Нельзя обойти обещание переименованием сущности: dockable widgets
не перестают быть workbench только потому, что называются modes или presets.
