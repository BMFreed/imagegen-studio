# Проверка гипотезы о контексте UI-компонентов

Дата: 2026-09-22. ImageGen Studio, исходная ревизия `8685c06b9761878f7baf15567cc2d8fceb1e3de9`.

Дополнительные справки не улучшили измеряемый результат: все 24 реализации прошли независимые критерии, все предварительные объяснения получили максимальный балл. Исходная гипотеза о спонтанном недоборе контекста остаётся открытой, поскольку подробный предварительный разбор был обязательным для всех. Подтверждены пробелы прежнего тестового покрытия и противоречия существующей документации.

## Вопрос и граница вывода

Проверяем, помогает ли дополнительный контекст об API Naive UI и композиции приложения исправлять повторяющиеся дефекты интерфейса. Отдельно оцениваем объяснение механики до правки и поведение готовой реализации.

Это пилот на трёх конкретных задачах, а не оценка всей библиотеки, всех моделей или эстетического качества интерфейса. Он не сравнивает Naive UI с чистым Vue. Он также не проверяет спонтанный поиск контекста при расплывчатом запросе: все участники получили точные требования и обязательное объяснение механики до редактирования.

## Дизайн

24 участника с новым контекстом: три задачи × четыре условия × два повтора. Одинаковая унаследованная конфигурация модели, без переопределений; порядок распределения перемешан с seed 22092026. Не более трёх участников одновременно. Каждый работает в отдельной копии одного исходного состояния; зависимости общие и только для чтения. Изоляция логическая, не отдельный системный sandbox.

| Условие | Дополнение к исходному репозиторию |
| --- | --- |
| A | Нет дополнительной справки |
| B | Механика Naive UI: размеры/слоты/состояния кнопок, select/input API |
| C | Композиция приложения: общие компоненты, DI, границы состояний и действий |
| D | Обе справки |

У всех одинаковые TASK, AGENTS, UI skill и доступ к исходникам установленных зависимостей. Поэтому сравнивается удобство получения уже доступной информации, а не наличие доступа к ней. Справки различаются длиной и содержанием; это не эксперимент с одинаковым числом токенов.

Задачи:

1. **Иконки.** Размер 18×18 у заданных действий Project, отдельная проверка области иконки и кнопки, центрирование, сохранение hit area и поведения после переноса в нейтральный контейнер.
2. **Карточки.** Единая поверхность выбора/hover у Raster, Smart Patch и Regional Guidance, независимость вложенных контролов, клавиатура, постоянные детали без layout shift, сохранение DI.
3. **Выбор ресурса.** Rich options, включая уже выбранный ресурс, компактное закрытое значение, поиск по трём полям, disabled/keyboard/clear, имена реальных native inputs, два независимых model bindings. Общая заранее подготовленная страница и fixture неизменны.

На участника выделено 18 минут активной работы. До реализации сохраняется PRECHECK; после — EVIDENCE и RESULT. Собственные проверки и исправления разрешены до сдачи; результаты независимой оценки участникам не возвращались, доработки по ним не заказывались.

Независимый оценщик подготовил браузерные проверки и шкалу PRECHECK до просмотра результатов. Код и шкала зафиксированы контрольными суммами. Он не получал таблицу соответствия ID и условий; координатор её знает и не является слепым оценщиком. В текстах участника могут встречаться косвенные признаки полученной справки — абсолютное ослепление не гарантируется.

## Проверка чувствительности измерения

Общий исходный вариант прошёл существующий набор из **112 тестов**. При этом независимые проверки обнаружили ожидаемые дефекты:

| Задача | PASS в исходном варианте | FAIL в исходном варианте |
| --- | ---: | ---: |
| Иконки | 33 | 19 |
| Карточки | 25 | 8 |
| Picker (заготовка) | 1 | 17 |

Отдельная эталонная реализация picker прошла 18/18. Это проверяет, что измеритель различает исходные дефекты и исправленное поведение. Числа — assertions, а не число независимых багов или наблюдений. Единица сравнения — работа участника; нельзя трактовать сотни assertions как сотни независимых экспериментов.

Зелёные 112 исходных тестов одновременно с красными проверками карточек/иконок — прямое свидетельство пробела прежнего покрытия. Наличие тестов и общий PASS сами по себе не подтверждали нужные пользователю состояния.

## Итоги

**Дополнительные справки не дали измеримого выигрыша в этом пилоте.** Все 24 участника правильно объяснили проверяемые механизмы по заранее зафиксированной шкале и довели свои решения до прохождения независимых критериев.

| Условие | Финальные browser checks: полностью прошедшие работы | PRECHECK, средний балл | Независимый typecheck |
| --- | ---: | ---: | ---: |
| A — без справок | 6/6 | 8.0/8 | 6/6 |
| B — API библиотеки | 6/6 | 8.0/8 | 6/6 |
| C — композиция приложения | 6/6 | 8.0/8 | 6/6 |
| D — обе справки | 6/6 | 8.0/8 | 6/6 |

Итог: **24/24** работы прошли все назначенные проверки, **824/824 assertions** успешны, **24/24** отдельных typecheck завершились с exit 0. По задачам: каждый из 8 вариантов иконок — 52/52, карточек — 33/33, picker — 18/18. Веса задач/участников равны; большее число assertions у иконок не делает их более многочисленной выборкой.

PRECHECK оценивался до чтения реализации и её результатов. Все четыре измерения получили 2/2 у каждого участника; цитаты и причины сохранены отдельно. Это подтверждает покрытие заданных вопросов, а не исчерпывающее знание библиотеки. Координатор сверил цитаты с сохранёнными PRECHECK и выборочно прочитал объяснения контрольной группы.

Полные регрессионные наборы по отчётам участников: **23/24** окончательных прогонов полностью зелёные; у R11 сохранился один timeout с успешным неизменённым точечным повтором, подробнее ниже. Самостоятельно проверены typecheck и отдельные зафиксированные browser criteria для всех 24. Результаты полных наборов и их логи не выдаются за 24 повторных полных запуска координатором.

Отдельный просмотр исходников подтвердил соответствие границам задачи и архитектурным требованиям у **24/24** работ: сохранены DI и независимые модели, нет общего изменения плотности темы или посторонних команд. Защищённые harness/fixture/config/instructions не изменены участниками; исходные материалы, критерии и сданные файлы совпадают с сохранёнными контрольными суммами. Это проверка заявленных границ, а не утверждение об идеальности всех решений.

**Гипотеза «агент обычно сам не добирает контекст» осталась открытой.** При явном требовании разобраться агенты контрольной группы смогли корректно объяснить источники размеров, слотов, событий и native attributes. Это не показывает, стали бы они делать такой разбор без требования. Одинаковые максимальные оценки и итоговый PASS означают потолок данного измерения: оно не различило условия, а не доказало их универсальную равноценность.


## Повторяющиеся ошибки по пути к результату

Эти наблюдения получены из сохранённых отчётов участников и доступных логов; это не полный журнал всех действий и не заранее зарегистрированная метрика первого патча.

- При добавлении выбора всей карточки проверки поймали ошибку `event.target.closest(...)`: обработчик вложенной кнопки менял SVG, поэтому к моменту всплытия target уже не находил родительскую кнопку. Использование исходного `event.composedPath()` устраняло непреднамеренный выбор слоя. В отчётах всех 8 участников задачи карточек зафиксирована эта промежуточная ошибка, включая обе реализации каждого условия.
- Перенос иконки в штатный icon slot сохранял требуемые 18×18, но менял inline baseline контейнера кнопки сворачивания. Существующие проверки ловили сдвиг примерно **0,898 px**; локальный flex у контейнера восстанавливал центрирование. В отчётах всех 8 участников задачи иконок зафиксирован этот промежуточный сдвиг, включая обе реализации каждого условия. Справки о размерах не предотвращали именно эту ошибку композиции.
- Часть неудачных прогонов относилась к новым тестам: попытка обычного Playwright click по disabled option, ожидание удаления скрытого DOM меню вместо скрытия, выбор одновременно из уходящего и нового dropdown. Это ошибки измерения/фикстуры, их нельзя смешивать с дефектами конечного UI.

## Дополнительный проверяемый дефект контекста

Это находка при чтении отчётов, отдельно от зарегистрированных метрик. R22 указал на рассинхронизацию документации; координатор проверил её в исходном основном checkout:

- [layer-stack.md](../features/project/generate-mode/layer-stack.md), строки 153–156, утверждает отсутствие inline prompt/reference authoring и Compare generation settings.
- Там же строка 167 описывает selected-item details. При этом [ProjectEntitySurface.vue](../prototype-app/src/prototypes/project/ProjectEntitySurface.vue), строка 98, показывает details по наличию слота, без условия selected.
- [ProjectRegionalRow.vue](../prototype-app/src/prototypes/project/ProjectRegionalRow.vue) уже содержит inline textarea (строка 159), добавление references (строка 94) и кнопку удаления (строка 220). [useCompositingLayerRow.ts](../prototype-app/src/prototypes/project/useCompositingLayerRow.ts), строки 32–35, уже формирует Compare generation settings.

Следовательно, проблема контекста может состоять не только в количестве прочитанного: часть доступных описаний противоречит реализации. Пилот не устанавливает, что именно эта рассинхронизация вызвала прошлые дефекты. Но перед наращиванием инструкций стоит устранить противоречия существующих описаний. В рамках эксперимента эти документы не исправлялись, чтобы не менять условия участников.

## Ограничения и сбои

- Только два повтора на комбинацию задачи и условия. Результаты описательные; статистическая значимость и универсальные выводы о моделях не заявляются.
- Точные требования и PRECHECK могли улучшить контрольную группу. В репозитории уже были корректные примеры resource select и существенная документация. Высокий итоговый PASS может означать потолок выбранного задания.
- Оценивается финальная реализация после собственных проверок. Это не безошибочность первой попытки.
- Полные tool traces и расход токенов через текущий интерфейс оркестрации недоступны. EVIDENCE — самоотчёт, не независимая телеметрия чтений. Временные метки отражают turnaround, а не активный inference; сравнение стоимости/скорости не делается.
- R11: финальный полный прогон — 112 passed / 1 failed, timeout открытия Dynamic Prompt Preview. Тот же тест прошёл в более раннем полном прогоне и в повторной точечной проверке без правки кода (3/3). Причина не установлена; финальный полный прогон не переименовывается в зелёный.
- R15: первый полный прогон завершился exit 143 после 67 успешных тестов, без assertion failure. Причина неизвестна; неизменённый повтор прошёл полностью. Это не основание приписывать сбой условию контекста.
- Отключение питания прервало R19–R21. Продолжены те же агенты: R19 имел реализацию, R20 — PRECHECK, R21 ещё собирал контекст. Артефакты R01–R18 и контрольные суммы сохранились. Длительность отсутствия питания неизвестна; эти интервалы исключены из любых временных выводов.
- В скопированных репозиториях pnpm 11 пытался автоматически переустанавливать общую ссылку node_modules. Одинаковая инфраструктурная поправка `verifyDepsBeforeRun: false` применена ко всем копиям; установка зависимостей не выполнялась. У каждого отдельные порт и Vite cache.
- Браузерная проверка относится к Chromium и прототипу с mock state. Она не доказывает production persistence, выполнение генерации, переносимость на все браузеры или художественное качество.

## Что это означает для AGENTS.md и skills

Пилот не даёт оснований расширять AGENTS большим справочником Naive UI или менять UI-kit. Дополнительные справки не улучшили измеряемый финальный результат и балл объяснений. Это **не доказательство их бесполезности**: контрольная группа тоже была обязана подробно исследовать механизмы до правки.

Практическое решение по имеющимся фактам:

1. Закреплять повторяющиеся гарантии в общей композиции и её проверках: роль и размер иконки отдельно от hit area; единое состояние всей карточки; независимость вложенных действий. Экспериментальные реализации показывают выполнимость, но они ещё не интегрированы и не являются выбранным продуктовым патчем.
2. Существующий research/review процесс дополнять только конкретной проверкой затрагиваемой границы: кто владеет размером/состоянием/событием, что изменится вне текущего родителя, какой соседний контрол обязан сохранить поведение. Это инженерная рекомендация по обнаруженным сбоям, а не измеренный в этом пилоте эффект нового AGENTS.
3. Не дублировать версионный API в постоянно загружаемых инструкциях. Если делать справку, держать её рядом с общими компонентами и рабочими примерами, с указанием версии и проверяемых гарантий. Самостоятельная польза такого каталога здесь не установлена.

Следующий различающий эксперимент должен сохранить одинаковую задачу и обязательные финальные проверки, но убрать PRECHECK у части участников. Желателен дизайн 2×2: дополнительная справка есть/нет × явный предварительный разбор есть/нет. Заранее нужны журнал реальных чтений до первой правки и зафиксированный первый патч, чтобы измерить пропущенный контекст и первоначальные дефекты, а не только результат после ремонтов. Текущий интерфейс оркестрации не дал полной телеметрии — её придётся обеспечить отдельно. Этот следующий этап не запускался.

Сравнение с чистым Vue ответит на другой вопрос: сколько ошибок и работы добавляет выбранная библиотека при равных требованиях к доступности, keyboard/disabled, теме и состояниям. По нынешнему пилоту замену библиотеки обосновать нельзя.

## Воспроизводимость

Полный локальный [стенд и индекс артефактов](~/Work/ui-context-study-20260922/README.md): `~/Work/ui-context-study-20260922`.

Среда: Naive UI 2.44.1, Vue 3.5.39, Vite 8.1.3, Playwright 1.61.1, Node 24.16.0, Chromium 153.0.8010.52. Условия среды сохранены в `environment.json`.

- `protocol.md`, `materials/`, `allocation.json`, `preregistration-sha256.json` — дизайн, задания, справки, распределение и исходные хеши.
- `judge/evaluate.mjs`, `judge/PRECHECK-RUBRIC.md`, `judge/freeze.json` — зафиксированные критерии; `judge/baseline-summary.json` — чувствительность на исходнике и эталоне.
- `runs/Rxx/` — отдельные репозитории участников; `artifacts/Rxx/` — PRECHECK/EVIDENCE/RESULT, патчи и хеши файлов.
- `artifacts/Rxx/browser/results.json` — результаты независимого браузерного запуска; `independent-typecheck.json` — отдельный запуск компиляционной проверки.
- `participant-suite-status.json` — результаты полных наборов по отчётам участников, с указанием происхождения; это отдельная категория доказательств от независимых проверок.

- `judge/implementation-review.json`, `judge/implementation-review.md` — отдельная оценка исходников и границ проверки.
- `combined-results.json`, `run-results.csv` — результаты всех работ с условиями и отдельными метриками.
- `browser-scores.csv`, `integrity.json`, `environment.json`, `events.jsonl`, `infrastructure-observations.md` — сводки и границы эксперимента.

Реализации участников не перенесены в основное приложение. Этот отчёт не повышает статус продуктовых promises и не изменяет правила AGENTS или skills.
