# Аудит UI-прототипов ImageGen Studio — 21 сентября 2026

## Вердикт

Информационная архитектура выглядит жизнеспособной: Home организует документы, Project содержит творческую работу, модели и пресеты имеют отдельные места управления. Но Project пока лучше демонстрирует набор компонентов, чем завершённый рабочий цикл. Основной риск — не внешняя «некрасивость», а недостаточная ясность контекста, ненадёжность некоторых действий и незавершённое повторное использование результата.

Для человека, знакомого с diffusion-инструментами, первый Generate достижим. Для обычного пользователя интерфейс требует слишком много предварительных знаний: какой объект сейчас генерируется, к чему относится Size, чем просмотр отличается от принятия, как вернуться к настройкам удачной картинки. Повторная работа затруднена даже для опытного пользователя.

Это экспертная оценка интерфейса, а не исследование с участниками. Время выполнения задач, обучаемость и частота ошибок реальных пользователей не измерялись. Оценки по десятибалльной шкале здесь дали бы ложную точность.

## Контекст продукта, который следует сохранить

Целевая аудитория включает обычных людей, желающих генерировать и дорабатывать изображения. Доменные сущности: проект, холст, модель и точная версия, промпт, слой, локальная правка Smart Patch, временный вариант, принятый результат, настройки результата, пресет.

Главная ценность продукта — возможность вернуться к удачному результату, понять настройки и аккуратно использовать их в новом эксперименте. Поэтому наличие формы Generate само по себе недостаточно.

Сохраняемые ограничения:

- Готовая композиция экранов; локальный resize/collapse допустим, произвольный docking не нужен.
- `.igs` принадлежит пользователю; Save и восстановление — разные операции.
- Generation Results временны; только явное принятие создаёт Layers/Variants.
- Обычная генерация использует настройки проекта; Smart Patch — свой draft. Размер документа и внутренний размер патча не взаимозаменяемы.
- Preset копирует выбранные настройки; не создаёт живую привязку проекта к пресету.
- Сравнение provenance только читает данные. Создание пресета из результата — отдельное действие. Прямой Recall/Restore не входит в этот MVP-контракт.
- Prompt остаётся обычным текстом CodeMirror; embeddings имеют sidecar references, LoRA-триггеры — контекстную подсветку. Возвращать chips ради компактности не следует.
- ControlNet, Upscale и полноценное редактирование Raster-пикселей не следует добавлять только ради сходства с InvokeAI.

## Что уже работает хорошо

1. Понятное разделение документов, настроек генерации и библиотек. Home и менеджеры дают хорошую основу для масштабирования.
2. Generate постоянно доступен, даже при прокрутке настроек. Это полезно сохранить.
3. Обычный текстовый prompt и общий редактор между поверхностями снижают стоимость обучения. Нативное выделение проверено существующими тестами.
4. Просмотр candidate отделён от набора принимаемых результатов: фокус на candidate 3 не включает его checkbox и не меняет `Add 2 as Layers`.
5. Раннее принятие выдаёт понятное подтверждение: незавершённые задачи будут отменены, остальные временные результаты отброшены.
6. Принятие создаёт слои/варианты, а не неявно заменяет выбранный Raster Layer. Undo/Save/dirty guards покрыты прототипными тестами.
7. Модель и embedding ошибки хотя бы частично объясняются текстом. Избирательное применение пресета технически умеет разблокироваться после снятия проблемной секции.
8. Выбор Smart Patch корректно меняет выбранную строку и хранит отдельный prompt. Подозрение на постоянное рассогласование выделения было опровергнуто после ожидания обновления UI.

## Приоритетные воспроизводимые дефекты

P1 ниже означает приоритет следующего прохода по прототипу. Это не утверждение об обнаруженной потере production-файлов.

### F01 · P1 · Повторный Generate молча выбрасывает текущие результаты

**Trigger:** Project → Generate → дождаться четырёх результатов → снова Generate, ничего не принимая и не отбрасывая.

**Факт:** было 4 completed candidate, стало 0 completed в новом наборе из 4; подтверждений нет. Старый staging и очередь заменены. Сохранённые слои не затронуты, но пользователь теряет временный набор для выбора/сравнения.

**Причина:** `ProjectPrototype.vue:90`, присваивания новой `queueItems` и новой `staging` на строках 107 и 126; Generate не имеет guard на существующий staging.

**Основание:** PP-002, PP-008; действия Generate и Discard должны быть различимы.

**Варианты:** (а) добавлять следующий запуск в существующий просмотр с ясными границами запусков; (б) для первой версии — перед заменой явно предложить завершить выбор или подтвердить отбрасывание. При смене цели Project/Smart Patch не смешивать результаты разных владельцев.

**Приёмка:** повторный Generate не уничтожает существующие candidates без явного решения; cancel перехода сохраняет и кандидаты, и selection; Generate без staging работает как раньше.

### F02 · P1 · Cancel не остаётся отменой

**Trigger:** Generate → через короткое время Cancel current generation.

**Факт:** candidate 1 сначала `canceled`, спустя менее секунды — `completed`. В очереди он также завершён. Пользователь не может доверять Cancel.

**Причина:** `ProjectPrototype.vue:143` меняет статус, но запланированный callback завершения (`runNext`, строки 70–88) позднее безусловно выставляет completed.

**Вариант:** завершать конкретную операцию только если она ещё активна; отменять её mock timer и игнорировать позднее завершение. Для production сохранить тот же пользовательский invariant на реальном worker boundary.

**Приёмка:** canceled остаётся canceled после исходного времени завершения; следующий job работает; отменённый candidate не становится принимаемым.

### F03 · P1 · Footer встроенного Apply Preset выходит за экран

**Trigger:** Project → Apply preset → Cinematic Img2Img Pass, viewport 1440×900.

**Факт:** footer начинается на y=938, Apply на y=949; первичное действие не находится в видимой области при открытии. Отдельный `?prototype=apply-preset` держит footer в окне.

**Причина:** `ApplyPresetModal.vue:151`: grid задан внешнему NCard, тогда как header, scroll и footer находятся внутри его content wrapper. Ограничение внешней высоты не образует ожидаемые три строки для реального содержимого.

**Вариант:** использовать штатные header/footer slots NCard и ограниченную прокручиваемую центральную область либо единственный grid на фактическом content container. Сохранять Apply/Cancel видимыми независимо от количества раскрытых секций.

**Приёмка:** весь footer видим на 1280×720 и 1440×900; длинный prompt и Expand all прокручивают только тело; действие достижимо мышью и клавиатурой.

### F04 · P1 · Недоступный ресурс блокирует Apply без объяснения

**Trigger:** тот же Cinematic Img2Img Pass во встроенном Project Apply.

**Факт:** Apply disabled, отдельного объяснения или маркировки проблемной LoRA нет. Снятие `Apply LoRA` разблокирует действие. В picker отсутствует Missing resource для этого вложенного ресурса; отображаются внутренние `imageToImage` и `smartPatch` вместо человеческих названий.

**Контроль:** Anime Clean Lines позволяет Apply. Standalone Apply показывает `Selected resource is missing` и пояснение.

**Причина:** `ApplyPresetModal.vue:33` вычисляет блокировку, но не выводит её причину. `ProjectPresetCard.vue:62` проверяет только верхний уровень payload. Нормальный nested helper уже существует.

**Основание:** PP-006 и явно зафиксированный known gap в `docs/features/presets.md:311`.

**Вариант:** общий источник diagnostics для picker, manager и integrated Apply; назвать ресурс и секцию, предложить снять секцию, заменить ресурс или открыть его в Model Manager. Не устанавливать и не заменять автоматически.

**Приёмка:** предупреждение видно до применения; выбранная missing-секция блокирует; снятая не блокирует; непереносимые/невыбранные данные проекта не меняются.

### F05 · P1 · Холст меняет пропорции при изменении доступного места

**Trigger:** staging, 1280×720 → Collapse layers panel.

**Факт:** документ остаётся 888×1184 (отношение 0,75), но видимая рамка меняется примерно с 173×203 (0,85) на 285×213 (1,34). Портрет становится горизонтальным. Это не просто маленький zoom, а искажение формы изображения.

**Причина:** `ProjectCanvasWorkspace.vue:422`: относительная ширина, min-width и max-height одновременно ограничивают рамку; высота перестаёт следовать aspect ratio. `fitView():144` всегда возвращает scale=0.62 и не вычисляет fitting. При 1440×900 исходное изображение — всего около 226×302 px в центре значительно большего viewport.

**Основание:** PP-001, canvas-toolbar/image geometry contracts. Наличие CSS mock не требует искажать видимые пропорции.

**Вариант:** отделить размер документа от camera scale; единообразно масштабировать обе оси; fit вычислять по доступной ширине/высоте с отступом. Учитывать tray и collapse. В InvokeAI `CanvasStageModule.fitRect()` делает именно геометрическое вписывание.

**Приёмка:** отношение сторон сохраняется при resize/collapse/tray; Fit реально использует доступное место и меняет только viewport, не документ.

## UX и визуальная композиция Project

### U01 · Высокий приоритет · Скрыта смена владельца настроек

После выбора Hand Repair Patch левая панель всё ещё начинается с `Create / Generate / Preset / Size`; нет устойчивого обозначения «Настройки Hand Repair Patch». При этом изменение prompt действительно относится только к патчу: контроль с переключением на Portrait Base это подтвердил. Size продолжает менять Project Canvas, хотя соседние поля уже относятся к patch draft. Apply также говорит лишь имя проекта.

**Последствие:** пользователь должен помнить неявную привязку через выбор справа; легко изменить не тот контекст или ожидать другой размер результата.

**Решение:** компактная постоянная строка цели рядом с Generate: «Весь холст» / «Патч: Hand Repair Patch». Тот же контекст — над prompt и в Apply/Save Current as Preset. Size явно назвать «Размер холста»; внутренний размер патча показывать в настройках патча. Не возвращать технический переключатель txt2img/img2img.

**Критерий:** до Generate человек может назвать цель, владельца редактируемых настроек и место будущего результата без пробного запуска.

### U02 · Высокий приоритет · Плотность не соответствует важности

На 1440×900 первые ~850 px левой колонки занимают Create, отдельная карточка Preset, Size, prompt, negative prompt и LoRA. Generation/Model начинается у нижней границы; основные sampling-поля ниже. При этом короткий positive prompt занимает лишь часть выделенной высокой области, а правая колонка имеет много свободного места. На 1280 это сильнее.

Текущий порядок и размеры во многом следуют существующим feature docs. Это основание пересмотреть сам UX-контракт, а не обвинять реализацию в несоблюдении выбранного порядка.

**Вариант A — рекомендованный, умеренный:** сохранить три колонки и fixed Generate. Сделать Preset компактной строкой, дать Size компактное summary с раскрытием, показывать модель/версию в устойчивой сводке, сохранить удобное текстовое поле prompt и его ручной resize. Negative/LoRA/secondary settings раскрывать с содержательными summary. Изменения высоты prompt согласовать с уже выбранным контрактом девяти/четырёх строк.

**Вариант B — более заметная переработка:** отдельные верхние секции «Описание» и «Параметры», но с постоянно видимой сводкой скрытых активных параметров. Риск — важные overrides становятся менее заметны; сначала проверить вариант A.

**Критерий:** на 1280×720 доступны цель, prompt, модель/версия и Generate; после раскрытия деталей ясно, что включено. Пользователь не обязан перестраивать панели перед первой работой.

### U03 · Средний приоритет · Слишком много равновесного оформления и мелких действий

Рамками одинаково выделены Create, Preset, Size, оба prompt и блоки настроек; границы split-панелей дополнительно режут экран. Холст имеет постоянную зелёную рамку и заметную тень. На строках Layers постоянно видны visibility, lock, duplicate, delete и menu; многие кнопки 22×22, tools 26×26. Две очереди и две колонки prompt actions добавляют конкурирующие акценты.

**Решение:** сохранить нейтральную тёмную основу и зелёный акцент для действий/выбора; отделять секции прежде всего заголовком и интервалом, оставить рамку там, где она обозначает редактируемую область. Снизить контраст неинтерактивной рамки холста и checkerboard. Второстепенные duplicate/delete/move сгруппировать в доступное меню; visibility и selection оставить сразу. Для часто используемых маленьких кнопок увеличить target примерно до 28–32 px без увеличения всех полей.

Это локальная система иерархии, а не предложение сменить тему целиком. Не следует компенсировать тесноту уменьшением всего текста.

### U04 · Средний приоритет · Просмотр и принятие объяснены недостаточно на самом холсте

Модель selection правильная, но на холсте не написано, какой временный результат сейчас показан; та же зелёная рамка используется у обычной композиции. В tray технические `completed/running`, одинаковые бейджи и маленькие checkboxes конкурируют с изображениями. `Clear` значит снять выбор, а соседняя корзина — потерять результаты. На узком экране заголовок и status переносятся, thumbnail-поле сжимается.

**Решение:** на холсте показывать «Предпросмотр 3 из 4 · ещё не добавлен» и действие возврата к композиции; в tray различать «Просматривается» и «Выбрано для добавления». `Clear` → «Снять выбор». Успешному thumbnail не нужен яркий completed badge на каждом изображении; ошибки и progress должны быть заметнее. Сохранить явное `Add N as Layers/Variants`, добавить доступную навигацию предыдущий/следующий, не превращать focus в acceptance.

### U05 · Средний приоритет · Варианты Smart Patch сложно узнавать

Chooser существует: кнопка с иконкой круговой стрелки открывает Variant 1/2/3. Он не отсутствует и не просто циклически меняет значение. Но названия без миниатюр требуют помнить содержимое; сама иконка легко воспринимается как regenerate.

**Решение:** кликабельное «3 варианта», миниатюры, явный активный вариант и доступ к сведениям о его генерации. Всё остаётся внутри конкретного Smart Patch; отдельная Gallery не нужна.

### U06 · Средний приоритет · Рабочие controls смешаны с декорациями

Regional prompt принимает ввод, затем после blur возвращает исходный текст; dirty не возникает. Opacity/blend, global-negative switch, VAE/precision и значительная часть Model Manager controls также имеют задокументированную presentation-only границу.

Это известные prototype gaps, а не утверждение о production-потере данных. Но визуально доступная форма обещает редактирование и делает UX-тестирование неоднозначным.

**Решение:** в целевом прототипном сценарии подключить значимые controls к session/history. Для временно непроверяемых controls использовать честный read-only вид и отдельную карту покрытия для ревьюера. Не встраивать инженерные `outside the MVP canvas` и `prototype limit` в будущий пользовательский текст.

### U07 · Средний приоритет · Словарь и доступность не завершены

Примеры: `imageToImage`, `smartPatch` в picker; `Mask Revision 2`, `Internal Size`, `Check`, `CUDA allocation failed`; число 4 рядом с Generate без видимой подписи. ARIA snapshot объявляет число изображений и вес LoRA как textbox `Please Input`; labels на обёртках не всегда дают нужное имя фактическому input. Большинство icon buttons уже имеют полезные aria-label — эту основу следует сохранить.

**Решение:** человеческие имена workflow, «Изображений: 4», понятные описания веса/силы эффекта, actionable diagnostics с деталями по раскрытию. Проверять accessibility tree, keyboard focus и возврат фокуса, а не только наличие aria-атрибута в Vue source. Полный screen-reader/WCAG-аудит здесь не проводился.

| PP-002 — явное намерение | Частично, есть нарушения | Generate скрыто отбрасывает результаты; Cancel ненадёжен; есть формы без эффекта |
| PP-003 — понятные владельцы | В основном на уровне экранов, слабее внутри Project | Не обозначена смена Project/Smart Patch draft; неясно соотношение Size и размера патча |
| PP-004 — модели и версии | Представлена библиотека, не завершён путь | Install/repair/version lifecycle презентационный; версия Project недоступна для выбора |
| PP-005 — результат помнит настройки | Ключевой UI-путь отсутствует | В layer menu только Move up/down; нет comparison и создания preset из принятого provenance |
| PP-006 — безопасное повторное использование | Менеджер проработан сильнее интеграции | Встроенные diagnostics и footer Apply; handoff в Models; согласованность отображаемого Size |
| PP-007 — свой переносимый проект | Решения Save/dirty/close показаны | Это session mocks; файл, recovery и переносимость не доказаны |
| PP-008 — явное принятие | Хороший базовый acceptance | Повторный Generate, отмена, поздние события; production cleanup остаётся за границей |

Особенно важен PP-005. Нельзя считать прототип достаточным для проверки основной ценности, пока отсутствует путь «выбрать удачный принятый результат → посмотреть настройки → сравнить с текущими → создать отдельный пресет → применить». Рекомендуется прототипировать этот путь целиком на representative mock provenance до полного backend.

При этом comparison должен оставаться read-only, сравнивать с Current Canvas по существующему контракту и не подмешивать mask/bbox/internal resolution в preset. Seed/randomize и выбор точной версии модели тоже нужны для осмысленного повторного эксперимента; сейчас они отсутствуют или read-only, что прямо признано в generation-settings contract.

## Остальные экраны

**Home.** Самая понятная задача и заметный New Project. Хорошая база поиска, статусов, recovery и document tabs. На первом экране пустой inspector отнимает существенную ширину до выбора проекта; рассмотреть компактное/свёрнутое исходное состояние либо более содержательное приглашение. Workspace-строки выглядят как ряд обведённых кнопок, хотя это навигация. Уменьшение рамок и сохранение одного устойчивого active-state улучшит сканирование. Это улучшения, не блокеры.

**Preset Manager.** Разделение списка, метаданных и редактирования удачное. Проблема визуальной плотности — длинные ряды badges с названиями секций и несколько независимых scroll areas. Лучше показывать краткий состав, явно выделять missing dependencies и раскрывать детали. Самый важный следующий шаг — перенести зрелость standalone Apply в Project, а не продолжать украшать только manager.

**Model Manager.** Внешне выглядит наиболее «готовым», но его task coverage заметно ниже этого впечатления. Большой preview занимает верх инспектора, exact versions и действия уходят вниз. Для технической библиотеки важнее установленная версия, совместимость, зависимости и действие. Приоритет: интерактивный путь установки/ошибки/repair и выбора версии из Project; затем размер preview и плотность metadata. Не добавлять marketplace: URL-first — осознанная граница продукта.

## Предлагаемый порядок работ

1. **Вернуть доверие к действиям.** F01–F04: staging replacement, отмена, доступность footer, объяснение блокировки Apply. Добавить regressions через настоящий Project entry point с соседними успешными сценариями.
2. **Исправить холст и показать контекст.** F05 + U01: неизменные пропорции, настоящий Fit, понятная цель Generate и границы Project/Smart Patch/Size.
3. **Закончить основной продуктовый цикл.** PP-005, необходимые seed/version controls, integrated Apply, явные состояния недоступных ресурсов. Пока на mocks, но сквозным пользовательским сценарием.
4. **Сделать визуальный проход.** Компактные summary слева, приоритет изображения, меньше равновесных рамок/иконок, узнаваемые варианты, consistent labels и accessible inputs. Сначала на Project, затем Home/Managers.
5. **Проверить с целевыми пользователями.** Попросить без подсказок создать проект; назвать цель генерации; принять два результата; сменить патч без изменения общих настроек; объяснить disabled Apply; получить пресет из старого результата. Измерять успех, неверные предположения и обращения за помощью. Моки должны поддерживать эти задачи, иначе проверяется догадливость участника, а не UX.

Критерий готовности следующей версии: человек понимает «что редактирую / что произойдёт / что уже сохранено / как повторить» без чтения инженерных документов. Красивые скриншоты дополняют эту проверку, но не заменяют её.
