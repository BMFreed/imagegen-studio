## Progress gap found during qualification design

Confirmed by tracing the existing source: the Smart processor called the actual
worker without its supported progress callback, and Main exposed only ordinary
processor snapshots. Thus genuine Smart work could complete without the Project
or Queue showing actual denoising steps. The qualification's correlated positive
progress oracle must remain; removing it would hide this UI integration gap.

The correction is transient telemetry (medium consequence), not a worker wire,
queue, persistence or numerical-policy change. Smart owns its validated monotonic
job/document/statusSequence progress, disables reception before Cancel waits and
before world output/publication, and ignores late/foreign callbacks. A common
app-lifetime progress source merges ordinary and Smart notifications with one
monotonic revision so switching operation kind cannot discard newer observations
or let an old null clear the current job. Existing schema and renderer ownership
checks remain. Test monotonic steps/totals, cancellation/late completion,
observer isolation and ordinary→Smart→ordinary revision handover. The trained
runner continues to require actual correlated steps, a rendered
`Denoising step N of M` counter and installed PID/executable observations.
Installed Python remains unchanged.

so this was a transient false repair notice rather than proof of a persistently
broken runtime. The underlying scope is advisory readiness, separate from job
admission and physical-exit ownership; the existing Runtime management contract
(`docs/specs/07-python-runtime-management.md`) distinguishes actual repair from
an environment used by an existing job.

Confirmed source mechanism: `GenerationActionController.getState` refreshes
`RuntimeManager.getStatus`. The generation lease remains `running` while its
healthy client closes. `GenerationWorkerClient.close` makes `ready` unavailable
before awaiting physical exit; the advisory check then treats the lease as
unready and publishes the repair kind. The regular successful close itself does
not create a global unconfirmed-exit fence. A separate legitimate unexpected
failure or unconfirmed close must continue to block all new work.

Prospective medium-risk correction: an owner-local `closing` lease phase,
entered only after verifying this client's qualified handshake immediately before
an explicit normal close. Status may defer probing under that same pointer/config
identity while actual admission/metadata still refuse another owner. A rejected
close changes to `unconfirmed-exit`; previously failed clients, changed metadata
and global exit fences remain fail-closed. Cover both callback-initiated and
runtime-finally close with observable barriers, plus unexpected-failure and
unconfirmed-exit controls. The running trained baseline stays source-frozen;
apply only after its physical exit and qualify the final source separately.
