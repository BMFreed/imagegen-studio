# Жизненный цикл локальных тестовых артефактов

Область — только `~/.codex/artifacts/imagegen-studio/`: данные, созданные агентом
для разработки и проверок ImageGen Studio. Это инструкция для агента, а не
фоновый очиститель или уже встроенная функция harness. Очистка входит в
разрешённую implementation/test работу; запрос только на анализ остаётся
read-only. Сейчас менять существующие данные ради применения этого документа
не требуется.

## Почему нужна очистка по завершению прогона

07.10.2026 папка занимала около 62 GiB: `installed-runtime` — 23 GiB,
`installed-cfg-rescale` — 13 GiB, `public-outpaint` — 24 GiB. Основной объём —
Python environments, копии весов и caches, а не сами отчёты. Последующие VAE и
embedding проверки переиспользовали каталог/runtime из `public-outpaint`.
Дата в имени не означает, что каталог больше не нужен.

В текущих инструментах [provisioner](../../scripts/provision-qualification-runtime.mjs)
создаёт environment на его окончательном абсолютном пути и использует
`uv sync --link-mode copy`; [qualification runner](../../scripts/qualify-installed-generation.mjs)
через `--resume` читает `fixture.appData`, `qualification-runtime.json`, его
внешний `report` и managed files. Поэтому нельзя просто перенести venv,
удалить старую папку целиком или оставить runtime без его companion files.

## Перед запуском

1. Измерить общий размер и свободное место (`du -sh`, `df -h`), затем размер
   непосредственных дочерних каталогов (`du -h --max-depth=1`). Не печатать
   полный список файлов Python packages. Проверить, не удалён ли root уже;
   отсутствие папки означает пустой inventory, а не повод для shell fallback.
2. Проверить, можно ли использовать существующий runtime/catalog. Сверить
   lock/config/profile, installed worker payload и настоящую готовность worker;
   устаревший worker нельзя объявлять совместимым ради экономии места. Сохранять
   максимум один idle reusable тяжёлый комплект для текущей цепочки работ.
   Временно второй допустим для installer/migration/version-isolation проверки
   с указанным моментом удаления. Не объединять несовместимые fixtures и не
   обходить strict guards `--resume`.
3. Создавать evidence и временные payloads раздельно. Для нового прогона вести
   небольшой `artifact-lifecycle.json` в каталоге evidence: владелец
   (repository/task/run), проверяемая ревизия, state (`running`, `retained`,
   `disposed`), `lastUsedAt`, пути evidence/payloads, `dependsOn`/`usedBy` и причины
   `pins` с наблюдаемым условием освобождения. Это запись для агента; текущий
   harness её автоматически не создаёт и не проверяет. Переиспользование
   чужого каталога отражать в обеих записях, сохраняя полный dependency graph.
4. Планировать место для новых downloads, распакованных dependencies, моделей
   и временных копий. Не копировать набор весов/environment в каждый новый
   датированный каталог. Отдельная mutable копия нужна, если именно её изменение
   проверяет тест; hardlink к оригиналу для такого теста недопустим.

Тяжёлый qualification также требует реестра настоящих process/cgroup boundaries.
`memory.current` включает файловый кеш от проверки SHA больших весов, поэтому
два отдельных лимита12GiB не означают общий лимит12GiB. Если KDE вынес native
Main/worker в отдельный owned scope, launcher может иметь меньший бюджет;
подтвердить реальные группы и их владельцев до выбора лимитов. Сохранять
`memory.stat` (как минимум anon/file), zero-swap, deadline и общий watchdog,
не увеличивать совокупный потолок только ради кеша. Ограничение
`MemoryMax<=12G` в guard задаёт максимум, а не обязательный размер launcher.
Прерванный watchdog запуск учитывается отдельно от semantic mutation:
сохранить исходный незавершённый report, независимый physical-exit proof и
фактические queue/receipt counts перед повтором. См.
[bounded dynamic embedding run](./phase-2c-illustrious-dynamic-embeddings-research.md).

Для будущих окружений подходит стабильный layout:

```text
shared/<runtime-identity>/provision-report.json
shared/<runtime-identity>/data/imagegen-studio/...
runs/<feature>/<run-id>/report.json
runs/<feature>/<run-id>/artifact-lifecycle.json
```

Provision выполнять сразу по этому пути. Уже созданные среды остаются на
оригинальном месте до освобождения зависимостей; этот layout не разрешает их
перемещение. Shared каталог также disposable, когда закончится его цепочка работ.

## Что сохранять и что освобождать

| Данные                                                                                                               | Действие после проверки                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Финальный report, delivery/hash manifest, fixture descriptors, команды, ревизии, relevant screenshots и bounded logs | Оставить компактный evidence set. Записать результат, ограничения и причины отброшенных setup failures в repo research note.                                                                                                                                                              |
| Существенный RED, его control/GREEN и restoration proof                                                              | Сохранять вместе; не оставлять только удачный screenshot или только имя теста.                                                                                                                                                                                                            |
| Build scratch, повторные downloads, временные model/environment copies, intermediates неудачного setup               | Удалить после сохранения диагностики, physical exit и проверки отсутствия зависимостей. Не оставлять их до следующего наполнения диска.                                                                                                                                                   |
| Project-owned package/download caches                                                                                | Удалять после завершения пользователей cache, если installed files независимы и все pinned companion/source files сохранены. Например, `uv` cache от завершённого copy-mode provision не требует хранить ещё одну копию packages. `cache` в имени само по себе не доказывает удаляемость. |
| Один текущий compatible runtime/catalog с нужными managed models и companions                                        | Оставить для следующего конкретного шага, указав причину и `lastUsedAt`. После подтверждённой замены или завершения цепочки удалить тяжёлый комплект, сохранив evidence. Не закреплять все исторические runtime «на всякий случай».                                                       |
| Mutation backups, изменённый installed payload, аварийные traces/data                                                | Держать до byte-exact restoration, независимого подтверждения startup и завершения расследования. После этого оставить компактное доказательство, а тяжёлые копии удалить.                                                                                                                |

Перед удалением payload сохранить source URL/credit, точные hashes, commands,
fixture descriptors и способ повторной подготовки. Секреты и model weights не
добавлять в Git. Нужные архивы/PNG для воспроизведения бага сохранять отдельно
как pinned evidence; hash не заменяет файл, если reproduction требует его bytes.
Не выдавать ссылку на удалённый локальный report за доступный сырой evidence.
В research note оставить итог и отметить, какие raw данные были удалены.

## Проверка зависимостей перед удалением

- Сначала записать точный список кандидатов, их размеры и основания удаления.
  Удалять по этому списку, без glob всей папки или отбора только по возрасту;
  непосредственно перед удалением повторно проверить paths и отсутствие новых
  пользователей. Metadata и исходные reports не переписывать так, будто
  удалённые payloads всё ещё существуют: результат прогона остаётся историческим,
  а факт очистки фиксируется отдельно в lifecycle/research note.
- Проверить владельца и canonical path каждого кандидата: это строгий потомок
  разрешённого artifact root, а не root целиком, его alias или другой mount.
  Не следовать symlinks и не удалять внешние targets. Обычное app data
  (`~/.local/share/imagegen-studio` либо пользовательский `XDG_DATA_HOME`),
  исходные модели/изображения за пределами root и глобальные caches не входят
  в разрешённую очистку.
- Сверить `dependsOn`/`pins`, fixture `appData`, `qualification-runtime.json.report`,
  runtime pointers и source/managed model/config/companion paths, а также
  сохранившиеся research references. Отчёт старого provisioner может быть
  небольшой, но необходимой зависимостью нового прогона. Историческая ссылка
  сохраняет только указанный raw evidence, а не весь environment навсегда.
- Дождаться настоящего завершения Electron, worker, installer, debugger и
  фоновых задач, использующих кандидата. Завершение CLI/родителя недостаточно.
  KDE может перенести Electron и worker в отдельный application scope;
  учитывать фактические PID/cgroup. Не завершать чужие процессы ради очистки.
- Убедиться, что свои semantic mutations восстановлены и больше не нужен
  rollback. Если cleanup пересекается с другими агентами, выбрать одного
  владельца очистки и согласовать использование shared paths с командой.
  Не запускать очистку одновременно с новым reader/writer того же каталога.

Нет достоверной ownership/dependency записи — сначала выяснить её по реальным
references. Возраст, отсутствие lock-файла или имя `tmp` не достаточны. Если
владельца выяснить не удалось, оставить данные и сообщить конкретную причину;
не считать их автоматически agent-owned и не создавать approval gate для
остальных заведомо своих безопасных кандидатов.

## Контроль роста и передача задачи

Начальные **операционные решения**, не измеренные пределы системы:

| Параметр                         | Значение и действие                                                                                                                                                                                                                                                                                         |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Soft budget всего root           | 30 GiB: при превышении до нового тяжёлого прогона разобрать самые большие каталоги, удалить доказанно свободные копии/caches либо записать необходимое исключение, потребность в диске и условие освобождения. Это ориентир для одного текущего ML комплекта вместо трёх накопленных; не hard limit модели. |
| Soft budget компактного evidence | 1 GiB: укоротить/сжать дублирующие logs, удалить избыточные screenshots и промежуточные прогоны после фиксации причины; сохранить final baseline и существенные RED/GREEN/restoration.                                                                                                                      |
| Исторические evidence sets       | Хранить последние три завершённых набора на feature/check. Более старые удалять только после переноса итогов в repo и подтверждения, что они не нужны для открытого бага, действующего promise/review evidence или воспроизведения.                                                                         |

Бюджеты запускают review/очистку, а не разрешают удалять active/pinned данные.
Если текущий обязательный ML комплект больше ориентира, назвать его actual size
и причину; не ослаблять проверки и не удалять необходимые модели. Бюджеты можно
пересмотреть по наблюдениям следующих прогонов, явно записав новое решение.

В конце каждого прогона, после recovery от interruption и перед handoff:
подтвердить physical exit/restoration, сохранить компактные доказательства,
освободить свои ненужные payloads, обновить lifecycle/dependencies. Измерить
root повторно. В отчёте кратко указать удалённые пути, размер до/после,
фактически освобождённое место и что осталось с причиной/условием удаления.
Не сообщать об очистке как выполненной, если добавлены только инструкции.
