# Naive UI, собственный API и собственная реализация: второй эксперимент

Дата: 2026-09-22. ImageGen Studio, исходная ревизия `8685c06b9761878f7baf15567cc2d8fceb1e3de9`.

**Замер даёт основания развивать небольшой общий API компонентов, но не обосновывает полную замену Naive.** Готовый слой сократил код потребителей и убрал повторяемые ошибки типов при сборке селекторов. Дополнительный выигрыш от собственной реализации под тем же API на этой выборке не установлен достаточно надёжно для решения о миграции: различие первых версий B/C связано с одной ошибкой импорта, финальные основные проверки проходят во всех условиях, а дополнительный аудит нашёл оставшийся UX-дефект у native-варианта.

Это продолжение [первого пилота о контексте](./ui-context-experiment.md). В первом исследовались справки при обязательном PRECHECK; здесь PRECHECK убран, инструментарий различается, а первая готовая версия сохраняется до самостоятельной проверки. Числа двух пилотов не объединяются.

## Что сравнили

18 свежих контекстов: 3 задачи × 3 условия × 2 повтора. Одна унаследованная конфигурация модели, без override; перемешанный порядок с seed 23092026; до трёх участников одновременно, максимум два test workers у каждого, бюджет 18 минут от dispatch. Все работали в отдельных копиях с одинаковыми fixture, темой, требованиями и соседним приложением. Изоляция логическая, не отдельный OS sandbox.

| Условие | Что получает участник |
| --- | --- |
| A | Прямые компоненты Naive; локальную композицию пишет самостоятельно |
| B | Готовые KitAction, KitSurface, KitResourceSelect поверх Naive |
| C | Те же компоненты с тем же публичным API на Vue и native HTML/CSS |

Документация, примеры и типы API B/C совпадают побайтно. Их готовые компоненты предварительно реализованы и проверены отдельно. A запрещены уже готовые обёртки приложения для целевых ролей; B/C предписано использовать соответствующий kit. Поэтому это сравнение организации работы с UI, а не свободный выбор инструмента. Shell во всех условиях остаётся общим и использует Naive: полной миграции приложения, bundle size или удаления зависимости не было.

Задачи проверяют границы из предыдущих дефектов:

- Панель: 32/24 px hit area, иконка и её allocation 18 px, перенос в контейнер с другим шрифтом и clipping, disabled/busy, клавиатура и tooltips.
- Карточки: единый hover и пассивный выбор по всей поверхности, постоянные детали, независимые range/notes/lock, сохранение редактирования и parent-driven обновления.
- Селекторы: два независимых поля с превью/base/triggers, компактное закрытое значение, поиск, disabled/clear/keyboard, обновления списка и native ARIA-связи.

**Оговорка о сохранении условия:** K17, назначенный в B, заменил внутри KitAction NButton/NIcon на native button и сохранил NTooltip. Это произошло уже до first. TASK разрешал расширять kit при сохранении API и явно не требовал сохранять NButton: защищённую область участник не нарушил, но получился гибрид, ослабляющий сравнение фиксированных внутренних реализаций. K17 остаётся в группе по назначению; его не исключали и не заменяли удачной попыткой. Остальные пять B сохраняют исходный backend, их first/final проходят основные проверки (5/5), но этот неполный срез не является новым сбалансированным сравнением.

Первый снимок неизменяемый и снят до post-change verification по инструкции; финальный — после самостоятельных исправлений. Обратной связи независимого оценщика участники не получали. Все 18 первых checkpoint явные, без автоматического fallback. Полного tool trace нет, поэтому отсутствие любой неинструментированной проверки до checkpoint не гарантируется на уровне ОС.

## Измеренный результат

| Условие | Первая версия: browser + types* | Финальная версия: browser + types* |
| --- | ---: | ---: |
| Прямой Naive | 4/6 | 6/6 |
| Общий API поверх Naive | 5/6 | 6/6 |
| Тот же API на Vue/HTML | 6/6 | 6/6 |

**Примечание.** Browser + types означает прохождение всех групп своей задачи и отдельного typecheck. Для hover карточек здесь используется одинаковая дополнительная проверка после завершения анимации; прозрачная поправка описана ниже. Это не утверждение об отсутствии всех UX-дефектов.

Независимый typecheck первых версий: **15/18**, финальных: **18/18**. Браузерных групп на задачу 12/13/16; группа может включать несколько утверждений. Единица сравнения — участник, а не отдельный assertion.

Различия первых версий имеют конкретные причины:

- **K09 и K18, прямые селекторы Naive:** обе попытки независимо получили TS4111 при доступе к дополнительным полям `SelectOption` и TS2322 у `node-props`, где не учтён `SelectGroupOption`. Браузерные сценарии уже проходили. После самостоятельных исправлений типов проходят и types. Это повторяемая цена работы с API библиотеки в данной задаче.
- **K17, обёртка над Naive:** участник изменил KitAction и импортировал отсутствующий `Loader2` из `@vicons/tabler`. Исходный kit такого импорта не содержал. Страница не загрузилась, поэтому упали все 12 групп — один дефект импорта, не 12 UI-багов. Импорт исправлен на существующий `Loader`.
- Остальные первые версии проходят основные проверки с учётом времени hover. Это снова частичный потолок измерения при точных требованиях, а не доказательство равной надёжности во всех задачах.

### Что основные проверки пропустили

Одинаковый дополнительный browser-аудит всех шести карточек, first/final и обоих начальных слоёв, нашёл неправильную связь `label` с range в **четырёх первых версиях**: K02/K03/K07/K08. Внутри `label` перед input стоял `output`, поэтому `label.control` указывал на OUTPUT и клик по подписи не фокусировал поле. K02/K07/K08 самостоятельно исправили связь; **в K03 final дефект остался**. K06/K11 проходят обе версии. Выбор слоя от таких кликов не меняется везде.

Это post-hoc наблюдение отдельно от первичного балла. Ошибка встречается с прямым Naive и с native-kit; поля в обоих случаях собирает потребитель. Она показывает границу общего компонента карточки: гарантии его поверхности не распространяются автоматически на произвольную композицию слотов. Нельзя читать таблицу как «18 идеальных интерфейсов».

У K10/K13, а также в диагностике K16, часть правок касалась загрузочной анимации и измерений SVG. У K10 подтверждены 18 px CSS-размер и allocation, но вращение квадратного контейнера увеличивает axis-aligned `getBoundingClientRect()`. Круговая дуга остаётся внутри прежнего радиуса: `viewBox=200`, `r=90`, `stroke-width=20`, центр 100. Поэтому увеличенная DOM-рамка сама по себе не доказывает визуальное увеличение рисунка. Эти события учитываются как работа по диагностике/настройке, а не автоматически как доказанные визуальные дефекты Naive.

Суммировать независимые реплики как стоимость последовательной разработки экранов нельзя: в реальной работе helpers могли бы переиспользоваться.

До участников подготовка обнаружила дефекты в обоих вариантах: native tooltip обрезался родителем; обе KitSurface неверно обрабатывали всплытие от заменённого SVG target; Naive selector пришлось переделать с NInput/Popover на требуемый NSelect. Всё исправлено до фиксации критериев и baseline. Это setup cost, не ошибки участников.

NSelect в подготовленном B и прямых селекторах потребовал адаптации ARIA через наблюдение за внутренним pending-option class. Обёртка централизует эту зависимость, но не устраняет её. Native-kit реализует поиск, клавиатуру, popup и состояние самостоятельно. Долгосрочная цена поддержки и обновления обоих вариантов не измерялась.

## Достоверность и ограничения

Оценщик зафиксирован до первого результата, `2026-09-22T19:33:16.668968Z`. При калибровке оба полных reference прошли 41 группу, stub не прошёл все 41 без инфраструктурных ошибок. Существующий набор из 112 тестов прошёл на общей базе и обоих окончательных references. Это соседний контроль, а не полное покрытие новых задач.

**Поправка C12 после начала измерения.** Raw evaluator читал hover через 240 ms, а у прямых Naive-карточек переход длился 300 ms. У K02 и K07 различались промежуточные RGB. Независимый аудит подтвердил повторяемость при 240 ms и равенство после завершения перехода. Исходный evaluator/raw результаты сохранены. Отдельная версия с ограниченным ожиданием конечных анимаций одинаково применена ко всем 12 карточным снимкам. Она меняет только время чтения, не требование равенства. Это post-freeze sensitivity analysis, не заранее зарегистрированная метрика.

Raw browser + types: first — A: 2/6; B: 5/6; C: 6/6; final — A: 4/6; B: 6/6; C: 6/6. Основная таблица явно использует вариант с ожиданием. Без этой оговорки можно было бы ошибочно приписать Naive два дополнительных дефекта.

У всех 18/18 участников последний записанный полный suite завершился успешно. Только у **12/18** его source hash совпадает с финальным и в начале, и в конце команды. У остальных файлы менялись во время прогона или после него; это отражено в приложении. Независимые browser/typecheck запускались на точных неизменяемых first/final снимках. Прямые команды и ручные browser probes не полностью охвачены инструментированием; число записанных проверок не равно числу всех исправлений. Токены, полный журнал чтений и активное inference time недоступны. Wall time включает общую машину, тесты и ожидания.

Проверены хеши условий, исходного оценщика, отдельной поправки и защищённых файлов. Source review выполнен отдельно от реализации; код раскрывает библиотеку, поэтому полной слепоты source review нет. Это маленький целевой пилот с двумя повторами, одной конфигурацией модели и подробными требованиями. Он не замеряет эстетическое качество открытой задачи «дополировать экран», спонтанный поиск контекста при расплывчатом запросе, все браузеры/screen readers/IME, большие списки или годы сопровождения.

## Решение для проекта

Сначала имеет смысл закрепить узкий публичный API повторяемых компонентов: icon action, layer surface, resource picker и составное поле с проверенной связью подписи. Публичный контракт должен описывать состояния, модель, slots/event zones, размеры и ARIA; исполняемые примеры должны проверять эти гарантии. Выбор внутренней реализации можно делать для каждого компонента отдельно.

Полный отказ от Naive по этим данным не рекомендован. Обёртки уже убрали повторяемые ошибки потребителя селектора и сократили его код, сохранив меньший подготовительный объём. Собственная реализация может быть оправдана там, где конкретные требования требуют нестабильного доступа к внутреннему DOM библиотеки; этот компромисс нужно оценивать отдельно. Самописность не заменяет контракты и проверки композиции.

AGENTS.md и skills в этом запуске не менялись. Практический следующий шаг — небольшой проверяемый каталог компонентов и ссылка на него из инструкций, с правилами выбора API и проверки состояний. Больше общих напоминаний «изучай библиотеку» не адресуют найденный дефект label, неполное покрытие и ошибки измерения анимаций. Этот запуск не интегрирует экспериментальный kit в приложение.
