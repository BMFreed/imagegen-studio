# Review через проверяемое поведение

Review проверяет пользовательский результат относительно обещания и supporting
contract. Чтение diff помогает выбрать проверки; исполняемый regression test
показывает конкретное нарушение. Успешный прогон подтверждает только проверенные
сценарии и границы, а не отсутствие любых дефектов.

Основа — work project `architecture/standards/review-protocol.md` и
`.claude/commands/mr-review.md`. Этот документ адаптирует их для GitHub, локальных
проверок и текущего Vue-прототипа. Предварительный контекст строится по
[Research protocol](./research-protocol.md).

## Применимость

- Low-risk copy/style: diff и визуальная/структурная проверка по месту.
- Medium-risk behavior/shared component: contract, реальные entry points,
  focused regression checks и соседний control case.
- Изменение promise или high-risk boundary: полный проход ниже, воспроизведение
  существенных behavioral findings и проверка чувствительности ключевых тестов.

Документационные promises проверяются на согласованность scope, negative scope,
acceptance criteria и evidence. Для них не нужно искусственно создавать runtime
red test. Review не заменяет UX, accessibility, security, architecture и code
health проверки. Существенный доказанный риск нельзя игнорировать только потому,
что дорогой или отсутствующий harness не позволяет автоматизировать его сейчас.

## 1. Вход и ревизия

Зафиксировать проверяемую ветку/commit и base SHA. Если предмет — dirty working
tree, назвать его явно и учесть uncommitted/untracked файлы; не выдавать проверку
HEAD за проверку этих правок. Для чужого PR проверять полученную head revision,
не полагаться на изменяемый `FETCH_HEAD`.

До diff прочитать ожидаемый результат, источник promise/feature contract,
acceptance criteria, инварианты и blast radius. Если утверждение нельзя вывести
из задачи и документов, зафиксировать недостающий продуктовый выбор. Не требовать
новый PP-ID, если уже есть подходящий локальный контракт.

## 2. Попытка нарушить обещание

До чтения реализации пройти running flow только по обещанию, если система
доступна. Если reviewer уже читал реализацию или сам написал изменение, назвать
проход self-review; независимым или слепым он не считается. Отсутствие runnable
контура также указывается явно.

| Класс нарушения | Пример ImageGen Studio |
| --- | --- |
| Умолчала | Missing embedding блокирует Apply без объяснения причины |
| Добавила лишнее | Apply меняет секцию, которую пользователь не выбрал |
| Соврала | Save показывает Saved до успешной записи; diff говорит Same при отсутствии provenance |
| Не дала результата | Import оставляет вечный progress после ошибки или comparison падает вместо diagnostic |

Явно объявленное ограничение из negative scope само по себе не нарушение.
Проверять также, действительно ли пользователь видит это ограничение в момент
решения, а не только в инженерной документации.

Затем прочитать diff и пройти стыки, на которые первый пользовательский сценарий
не попал: consumers, defaults, error handling, serializers, cleanup, IPC/worker
события, caches, silent fallbacks и UI diagnostics. Само наличие `catch`, cast
или `?? []` не является находкой — нужен достижимый механизм нарушения.

## 3. Измерение и red tests

Измерять результат в конце обещанного пути. Для Apply проверять видимое
предупреждение и изменённый Project; отдельно проверять сохранность source preset
и невыбранных секций. Для Save — файл после повторного чтения через настоящий
loader и поведение на отказ, а не только cleared dirty flag.

Выбирать самый низкий test layer, где нарушение ещё реально. Pure helper tests
подходят для parsing/matching; wiring и видимые diagnostics требуют UI flow;
atomic Save требует filesystem integration. Сквозной тест доказывает нарушение,
локализующий тест помогает назвать причину — не нужно заставлять один тест
выполнять обе роли.

Для behavioral finding:

1. Получить failing test или фиксированное reproduction на проверяемом состоянии.
2. Убедиться, что падение вызвано нарушением contract, а не fixture, selector,
   скрытым элементом, старой сборкой или отсутствующей зависимостью.
3. Проверить соседний control case. Для регрессии сравнить base/head; падение на
   обеих ревизиях может означать прежний дефект, а не дефект нового patch.
4. Assertions должны различать корректный результат, потерю и добавление лишнего.
   Они не должны требовать единственную внутреннюю реализацию: несколько
   корректных реализаций допустимы, ложноположительный пользовательский исход — нет.
5. Для high-risk ключевого invariant временно внести правдоподобную semantic
   mutation в изолированную копию и показать, что нужный тест падает. Затем убрать
   только свою mutation и подтвердить исходный результат.

Хотя бы один существенный integration test входит через настоящий entry point
проверяемого контура. Fixture builders валидируют форму входа и не скрывают
некорректные данные. Type assertions применяются к контрактам, которые должны
запрещать состояния; если состояние достижимо в runtime, нужен behavioral test.

## 4. Результат и приёмка

Находка содержит источник ожидаемого поведения, механизм, trigger, последствие,
файл/entry point и reproduction/test evidence. Отдельно назвать предположения,
которые были опровергнуты. Спекуляции без механизма не объявляются блокерами.

Для бага критерием исправления является тот же failing test, ставший зелёным
без ослабления assertions. Исправление ошибочного теста допустимо с объяснением,
почему он падал не по своей причине. Намеренная смена контракта фиксируется
отдельным продуктовым решением, а не подгонкой ожиданий под patch.

Reviewer не исправляет implementation без соответствующего scope задачи.
Test-only patch создаётся при разрешённой проверке исполнением; обычный запрос
на review сам по себе не требует commits, push, PR comments или изменения чужой
ветки. Такие действия следуют пользовательскому разрешению. Отдельная ветка с
красными тестами и changeset не являются обязательными артефактами проекта.

Если автоматизация несоразмерна или boundary ещё не существует, сохранить
reproduction/доказанный invariant и точное ограничение проверки. Critical risk
для данных или security сохраняет значимость при ручном доказательстве.
Невозможность наблюдать результат регистрируется как observability gap.

Один полный проход по рискам обычно достаточен. Второй независимый проход нужен
только при конкретном высоком риске и наличии разрешения на такую организацию
работы. Исправление ошибочного теста не считается новым поиском рисков.

## Проверки и отчёт

Текущие команды определены в [package.json](../../package.json):

- `pnpm run lint` — lint исходников;
- `pnpm run typecheck` — после TypeScript/Vue changes;
- `pnpm run prototype:test` — после prototype UI changes;
- `pnpm run prototype:build` — при изменении dependencies, imports или build;
- для docs-only — diff, local links/anchors и согласованность contracts.

Focused Playwright запуск: `pnpm run prototype:test -- tests/project.spec.ts`.
Он помогает локализовать проблему и не заменяет обязательный полный UI набор.
Production tests добавляются вместе с production boundaries; не подменять их
prototype runs. Для visual checks использовать штатные viewport scenarios и
проверять overflow, focus/keyboard behavior и console warnings по scope.

Отчёт указывает revision/working tree, promise, проверенные границы, commands,
число passed/failed/skipped, findings и gaps. Убедиться, что изменённый код попал
в проверку. Local validation, commit, push и CI — разные статусы. Если файлы или
неопределённость не изменились после успешных обязательных проверок, повторять
весь набор для ощущения уверенности не нужно.
