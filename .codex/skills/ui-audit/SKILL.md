# UI Audit

Проверь указанный участок глазами пользователя и объясни наблюдаемые дефекты.
Пользователю достаточно назвать элемент или приложить скриншот; технический
диагноз контейнеров и CSS агент получает самостоятельно.

## Граница задачи

- «Проверь», «проведи аудит», «что здесь не так» → исследование и отчёт;
  исходники UI, тесты и продуктовые контракты не менять. Скриншоты, заметки и
  временные данные для воспроизведения допустимы. Отдельное поручение сохранить
  отчёт позволяет записать его в репозиторий.
- «Посмотри и исправь» или последующее «исправь найденное» → диагностика,
  исправление разрешённых находок и проверка результата. Уже полученное
  разрешение не требует повторного подтверждения.
- Начни с названного элемента и его ближайшего контекста. Весь интерфейс
  проверяй только по соответствующему запросу. Не превращай локальную проверку
  в редизайн или аудит всех продуктовых обещаний.
- Сохраняй согласованные цвета, плотность и назначение экранов. Для существующего
  UI не запускай выбор новой дизайн-концепции из `frontend-design-principles`.
  Применяй [приоритет источников](references/visual-checklist.md#приоритет-источников):
  контракты задают требования, чек-лист помогает их проверить, общие рекомендации
  заполняют пробелы. Неразрешённые расхождения требований фиксируй отдельно.

## Что смотреть

Прочитай [визуальный чек-лист](references/visual-checklist.md). Он разделяет
видимые признаки, интерактивные проверки и допустимые исключения. Для конкретного
компонента прочитай его локальный контракт; полный код нужен после наблюдения,
когда проверяешь причину. Для подключения к приложению используй
[runtime guide](references/runtime.md) только если нет уже подходящей сессии.
Установка `playwright-interactive`, MCP или новых зависимостей не требуется.

1. **Зафиксируй контекст.** Electron или Vue-прототип, revision/working tree,
   экран, состояние данных и размер окна. Скриншот пользователя — указатель на
   проблему; при воспроизведении используй ту же поверхность. Прототип не заменяет
   проверку production renderer. При доступности только изображения обозначь
   результат как screenshot-only; поведение и причина в коде остаются непроверенными.
2. **Посмотри до диагностики.** Сними и действительно открой изображение с
   окружением элемента; одного DOM snapshot или сохранённого PNG недостаточно.
   Для мелких деталей добавь крупный фрагмент. Сформулируй наблюдение обычными
   словами: например, «список обрывается выше нижней границы модалки». Сначала
   оцени смысл и композицию, затем измеряй предполагаемую ошибку.
3. **Проверь применимые пункты.** Помимо исходного состояния проверь связанные
   с подозрением hover/focus, прокрутку, resize или повторное открытие. Выбирай
   соседний случай по механизму: пустой/заполненный список, короткое/длинное имя,
   feedback есть/нет. Не запускай все возможные состояния для одной кнопки.
   Действуй через обычный UI на временных данных; DOM/IPC используй для диагностики
   или подготовки fixture, а не как доказательство доступности действия пользователю.
4. **Подтверди находку.** Сопоставь скриншот с правилом, исключениями и назначением
   области. При необходимости проверь bounds, clipping ancestors, computed styles,
   слои перекрытия и API установленной Naive. Объясни влияние на пользователя.
   Отделяй наблюдаемый дефект от предполагаемой причины: причина может оставаться
   неизвестной. Большой отступ, несколько кнопок или scrollbar сами по себе не баг.
5. **Выдай отчёт.** Применяй формат ниже, без квоты на число проблем и общего
   «балла качества». Ноль подтверждённых дефектов — допустимый результат.
   Отдельно укажи непроверенные состояния и гипотезы. В режиме аудита закончи здесь.

Недоступный runtime не заменяй выдуманным воспроизведением. Укажи конкретный
блокер и доступное свидетельство (например, скриншот пользователя). Численные
проверки не опровергают видимое обрезание; расхождение нужно исследовать.

## Формат результата

Для одной локальной проблемы достаточно короткой записи; для нескольких используй
стабильные ID, чтобы пользователь мог выбрать, что исправлять.

```text
Область: экран / элемент; Electron, prototype или screenshot-only.
Контекст: revision/working tree, состояние, размер viewport, масштаб при необходимости.
Проверено: применимые пункты чек-листа и конкретные состояния.

UI-01 — краткое наблюдение; влияние: блокирует / мешает / косметика
Где и когда: элемент, шаги или состояние воспроизведения.
Факт: что видно; ссылка на скриншот/фрагмент, измерение при необходимости.
Основание: ID правила/локальный контракт; почему исключение не подходит.
Последствие: что затрудняется для пользователя.
Причина: подтверждённая с местом в коде либо явно обозначенная гипотеза/неизвестность.
Предложение: минимальное исправление с сохранением принятого оформления.

Ограничения: что не проверено; гипотезы отдельно от подтверждённых дефектов.
```

Приоритет определяется последствием: недоступное действие или скрытая ошибка
важнее косметической неровности. Не требуй трассу для статичной ошибки; для
динамической проблемы сохраняй последовательность кадров, видео или trace.

## Если исправление разрешено

Используй существующий компонент и публичный API Naive; для повторяемых controls
прочитай [контракты и потребителей](../../../docs/engineering/ui-component-contracts.md).
Проверяй техническую причину, а не маскируй её произвольным offset или сменой палитры.
Если изменение затрагивает общий компонент, проверь соответствующих потребителей.

После исправления повтори исходные шаги и соседний случай, просмотри результат
при сопоставимых данных и размере окна. Сохрани before/after. Выполни проверки
из `AGENTS.md` и [review protocol](../../../docs/engineering/review-protocol.md)
по реальному риску. Для обратимой локальной косметики достаточно проверки по месту;
не пиши тест, который лишь повторяет CSS-декларацию. Для существенного layout-бага
полезна проверка наблюдаемой геометрии, если цена соразмерна повторению дефекта.

В финале назови исправленное, фактически выполненные проверки и оставшиеся
ограничения. Не объявляй проблему решённой только по изменению кода или typecheck.
